Status (rewritten 2026-11-03, America/Toronto): **stage order revised by Nigel's decisions**; the research in sections 1-13 below is unchanged and still applies. Baseline `main` = v1.4.2 @ 2eb43bc. Work happens on branch `v1.5.0a` and later `v1.5.0b...g`; `main` is never touched until Nigel says so.

## 1. What the repo does today (facts, with paths)

Repo is on nigian at `~/nig-drives`, Vite + TypeScript + Three.js r180, Electron wrapper (`electron/main.cjs`, `preload.cjs`). ~14k lines of TypeScript under `src/game` + `src/*.ts`. **No test framework.** The only automated harness is `scripts/sim-bench.ts` (headless physics bench, built with esbuild). `.gitignore` already excludes `*.local`.

### Cars
- `src/game/vehicles/Vehicle.ts` (941 lines): `VehicleId` is a closed string union (`golf_18carb`, `golf_20aba`, `golf_19tdi`, `golf_28vr6`, `bus_diesel`, `bus_hybrid`, `model3_lr_awd`). `VEHICLE_SPECS: Record<VehicleId, VehicleSpec>` is the legacy arcade spec (mass, accel, wheelbase, track, gripMu, cgHeight, frontBias, L/W/H, camera distances, `ratedPowerKw`...). `class Vehicle` runs the 120 Hz step.
- `src/game/physics/PhysicsSpec.ts`: the real spec: `ChassisSpec`, `TireSpec`, `EngineSpec` (+`TurboSpec`), `GearboxSpec`, `ClutchSpec`, `DiffSpec`, `BrakeSpec`, `SteeringSpec`, `AssistDefaults`, `RegenSpec`, `EvSpec`.
- Hand-written physics specs: `physics/specs/golf19tdi.ts`, `physics/specs/model3LrAwd.ts`. Everything else (VR6, carb, ABA, buses) goes through `physics/deriveSpec.ts::derivePhysicsSpec(VehicleSpec)` (fixed torque-curve shapes per fuel, gearing solved from drag-limited top speed).
- **Meshes are three hand-coded builders** in `vehicles/VehicleFactory.ts` (720 lines): `buildGolf()` (shared by all four Golf engines), `buildModel3()`, `buildNewFlyerBus()`. They use `extrudeProfile(sideProfilePolyline, width, bevel)`. There is **no parametric/procedural body generator today**; "procedurally generated" only applies to derived physics specs. `createVehicle(id, transmission)` picks the builder by class.
- `vehicles/EngineSound.ts` picks a sound "character" from the vehicle id (`characterFor(id)`), so every new car needs a sound mapping.

### Tyres
- `TireSpec` has one set of numbers per car: `radius, widthM, mu, C, peakSlip, peakAngle, peakAngleRear?, loadSensitivity, rollingRes, relaxLength, inertia`.
- `physics/Tire.ts::tireForces(...)`: "Pacejka-lite" magic formula on combined slip, friction circle by normalising slip ratio and slip angle by their peaks; `SLIDE_FLOOR = 0.8` is a **global constant** (not per tyre); peak slip angle grows with sqrt(load).
- `VehicleSim.ts` builds `tireRear` from `peakAngleRear`; `fzNominal = m*g/4`.
- Weather/surface grip: `weather/Environment.ts::getGripMultiplier()` = clear 1.0, rain 0.62, snow 0.38. `map/RoadSurface.ts` has 12 surface kinds (asphalt 1.0, concrete .98, paving .88, cobble .78, compacted .82, gravel .65, dirt .55, grass .45, sand .4, ...), each with `wetRetain`/`snowRetain` and `noise`. `Game.ts` (~L480-490) passes `{roadFactor, grip, noise}` to the vehicle; `Vehicle.step` (~L563-571) clamps it and calls the sim.
- **Gotcha:** `p.tire.mu` is read directly in `Vehicle.ts` (L637 hill hold, L693 / L700-704 kinematic steering limit, L786 regen caps) and `Assists.ts` L96. A compound system must feed an *effective* `PhysicsSpec` into all of these, not just into `Tire.ts`.
- `SurfaceInfo` carries no surface *kind*, only a grip number. Compounds that care about loose surfaces need `kind` (or a `loose: boolean`) added to `SurfaceInfo`.

### Drivetrain, brakes, aero
- `DiffSpec { type: 'open'|'lsd', preloadNm, lockCoef }` exists, but **nothing reads it** (all cars are `open`). LSD is net-new physics, not a parameter change. AWD split is fixed by layout; there is no centre-diff model for ICE AWD (the Tesla's two motors are handled in `physics/Motor.ts`).
- `BrakeSpec { frontNm, rearNm, handbrakeNm }`: brake bias is already data-driven.
- Aero is drag only (`chassis.cdA`, used in `VehicleSim.ts` ~L189). **No downforce** term.
- `GearboxSpec.ratios / finalDrive / shiftTimeS` are plain data, so a gear-ratio setup sheet is cheap. `Powertrain.ts` has turbo (`TurboSpec`), torque converter (auto), clutch slip (`ClutchSpec.maxTorqueNm`).
- Assists: `physics/Assists.ts` (ABS, TCS, ESC), prefs in `ui/assistPrefs.ts`.

### Menus, input, persistence
- `ui/StartMenu.ts` (272 lines) is the only menu: class buttons (Golf / Tesla / Bus) -> variant row (`CLASS_VARIANTS`) -> transmission -> assist toggles -> quality -> city -> Start, plus a Dyno button. Output type `StartSelection {vehicle, cityId, transmission, quality, assists}`. `main.ts` wires it to `Game.start(sel)`. Styles: `.menu-card` / `.choice` / `.choice.selected` / `.section-label` / `.choice-row` / `.secondary-btn` in `src/style.css` (dark card, gold top border `#c9a36a`, blue choice tiles `#18233a`, selected cyan `#5ad4ff`).
- **There is no pause menu, no "back to main menu" path, no Options pane, no tutorial.** Esc only closes the Dyno and the expanded minimap. HUD has a static controls hint (`ui/HUD.ts` ~L100).
- `input/Input.ts` (258 lines): keys are **hard-coded `e.code` comparisons** (WASD/arrows, Space brake, Shift clutch, C camera, R weather, T time, P clock pause, E/Q or +/- shift, G auto selector, 1-6/N/B H-pattern, F1 assists, F2 Telemetry+). Gamepad = first pad, standard mapping, buttons/axes hard-coded (RT/LT/stick, B/X, bumpers 4/5, Y camera, button 8). No rebinding, no conflict detection.
- localStorage today: only `nigdrives.assists` (`{abs,tcs,stability}`) and `nigdrives.quality`. Nothing about cars, tyres, units, audio or bindings. Speed unit is hard-coded km/h in the HUD (`HUD.ts` ~L97).
- Audio: Web Audio master gain in `EngineSound.ts`; no volume setting.

### Race / AI logic
- **None.** Searching `src/` finds no AI drivers, traffic, checkpoints, laps, waypoints, routing, or ghosts. `map/RoadIndex.ts` has nearest-segment queries (`SegRef`, `NearestSeg`) which is the only road-graph-adjacent code; there is no connectivity graph for routing.

### World
- Elevation: `map/ElevationSampler.ts` reads AWS Terrarium PNG tiles (Mapzen/Joerd lineage, no key). Three samplers in `TileManager.ts`: **z14 near** (`new ElevationSampler(14, 128)`), z12 mid, z11 far. z14 is ~7 m/px at 43 N (but the underlying source data in Canada is coarser, ~20-30 m, upsampled; do not assume z14 means 7 m real detail).
- `map/Terrain.ts`: three nested heightfield rings: near ~1.2 km square (~6 m cells, carved to road corridors, cut/fill), mid ~4.8 km (~30 m), far ~16 km (~125 m). Quality presets set `nearRingRes` 128/192/... (`visuals/Quality.ts`).
- Roads: `map/RoadProfile.ts` smooths/grade-caps road heights; `map/RoadBuilder.ts` builds ribbons with miters, curbs, bridge sides; `CARVE_UNDER_ROAD / CARVE_SHOULDER` constants in `TileManager.ts`. **Road width is by `highway` class only** (`WIDTH_BY_HIGHWAY`, e.g. residential 6.4 m, primary 7.2 m); OSM `width`, `lanes`, `sidewalk`, `shoulder`, `barrier` tags are not read.
- Draw distance: `scene.fog = Fog(0x87b5e5, 350, 7000)` clear; rain 150-1600, snow 90-900 (`Environment.ts`). Camera far 12000, near 0.4. Tiles: `LOAD_RADIUS = 2` (5x5 tile window), unload at 4. Camera modes: chase / first (`camera/ChaseCamera.ts`, `C` toggles; the "first" view is a simple eye-ish offset, not a modelled cockpit).
- `cities.ts`: SF, Chicago, NYC, Toronto, Kitchener-Waterloo.
- Electron: `electron/main.cjs` only rewrites the User-Agent for Overpass mirrors; no CSP in `index.html`. Any new remote host (Cesium, HRDEM) needs adding to the Electron request filter list and, if a CSP is added later, to `connect-src`/`img-src`.
- `.env.local` on nigian now holds `VITE_CESIUM_ION_TOKEN` and `VITE_TOMTOM_API_KEY` (names only noted; values never read or printed). `*.local` is gitignored (verified with `git check-ignore`). Note: `VITE_*` values are **inlined into the JS bundle at build time**. See stage J for what that means for the Windows portable exe.

## 2. Research digest (what GT3/GT4 and Forza 4 do, and what we take)

### 2.1 Gran Turismo 2 car list (for the catalogue)
- Sizes differ by region/source: the NA Connoy database says **600 cars** (590 on v2.0, 600 with "lost Hondas" and two Nissans on v2.1+; split Japan 408 / USA 67 / Germany 43 / UK 40 / Italy 23 / France 19); the Japanese list says ~586; a PAL player reported as few as 539.
- **Our CSV: 621 rows from the PAL table (608 unique make/model/year strings; includes the Acura/Honda and Opel/Vauxhall duplicates, unnamed hidden cars shown as "-"). Collapsing trims/years/J-spec/race variants gives roughly 240 distinct make+model families**, which is the real unit of work (a "Skyline GT-R R32/R33/R34" family is 3 bodies, not 15).
- File: `~/nig-drives-logs/v150/gt2-carlist.csv` columns `make, model, year, drivetrain, aspiration` (here meaning "turbo option available" per the source, not stock aspiration), `stock_hp, stock_kg` (**in-game values from the source, reference only**), `max_hp`, `region_note` (JDM-only), `class` (`road/tunable`, `race`, `fixed-spec/race`). Years exist for ~365/621 rows (the source only prints a year where it disambiguates).
- **IP note:** GT's in-game numbers (dealer HP, in-game weights) are Polyphony data. The CSV keeps them only as a lookup aid for picking cars. **Shipped car data must come from real-world published specs, never from the GT columns.** Keep the CSV out of the repo (or in `docs/` as names only: make/model/year/drivetrain).
- Era mix (rows with a year): 1960s 13, 1970s 5, 1980s 20, 1990s 327. GT2 is a late-90s Japanese-heavy list (Nissan 93, Toyota 85, Honda 62, Mitsubishi 50, Mazda 48, Subaru 42).

### 2.2 GT3/GT4 tuning parts and effect sizes
GT does not publish formulas; effect sizes below are from magazine/forum measurements and are **targets for our own calibration**, not ground truth.

| Part (GT4 names) | GT behaviour / reported effect | Our mapping (section 5) |

| Port & polish, engine balancing, displacement up | small gains; balancing raises rev limit; displacement up only on some cars; permanent | small torque + redline |
| Turbo kit Stage 1/2/3/4 | forum figures ~+10 / +20 / +35 / "+125 %" for stage 4; S3 favours mid-high rpm, S4 peak hp | cap S4 at about +60 % |
| Intercooler Sports / Racing | more boosted power | +2 % / +4 % on boosted share |
| Supercharger | only for some NA engines; replaces NA tune | later |

| LSD 1-way / 1.5-way / 2-way / Fully custom (initial / accel / decel, 5-60) | accel lock for traction, decel lock for stability, too much hurts turn-in | new diff model |
| Driveshaft (carbon) | "no noticeable increase" | +0.5 pt efficiency, cosmetic |
| Brakes Sports / Racing; brake balance controller | forum testing: stopping distance is tyre-limited, brakes mainly add fade resistance and lock-up headroom; balance sheet 0-30 per axle | torque scale + bias slider |

| Centre diff / VCD (AWD) | front/rear split 5-50 | AWD split |

GT4 setup sheet (per axle unless noted): ride height; spring rate (10-20 index); damper bound and rebound (1-10); camber; toe; stabilizer (1-10); brake balance (0-30 F/R); downforce F/R; LSD initial / accel / decel (5-60, 5 about open); gear ratios + final; AWD torque split; power limiter and ballast.
Typical starting values from guides: camber about 1.7/1.2 deg (racing tyres) or 2.5/2.0 deg (sport tyres); brake balance 8-12 evenly; high LSD accel (45-50+) but avoid high decel.

### 2.3 GT3/GT4 garage, dealer, used cars
- GT3: new and used dealers merged by country/make; used lot shows 30 cars, six replaced per race/test (five advances to fully refresh). GT Auto: car wash Cr. 50, oil change Cr. 250.
- GT4: garage up to 1,000 cars; used lots split Historic (pre-1990) / Early 90s / Late 90s, refreshed every seven in-game days, no duplicate used cars; used sale pays 50 % (60 % with matching make).
- **Take for nig-drives:** garage + dealer as separate screens; dealer sorted by make/country/era; "Used" lot optional later (career); keep GT3's "stock rotates" idea only in career mode.

### 2.4 Forza Motorsport 4 ideas worth folding in
- **Performance Index (PI) classes** (FM4 bands): F 100-200, E 201-275, D 276-350, C 351-425, B 426-500, A 501-600, S 601-700, R3 701-800, R2 801-875, R1 876-998, X 999. PI is built from five sub-scores (speed, handling, acceleration, launch, braking, each 3.0-10.0) and *changes with upgrades but not with custom tunes*. We adopt the idea and the bands, with our own formula (section 5.4), computed by running our own sim.
- **Upgrade system with conversions:** engine swap (adds power, often weight; needs drivetrain/suspension upgrades), **aspiration conversion** (turbo / twin-turbo / supercharger / centrifugal; turbo favours top speed, supercharger-type favours twisty), **drivetrain swap** (RWD/FWD/AWD; weight and handling change a lot). Per-car availability lists exist (pez2k's FM4 conversion table). We adopt the three conversion slots with per-car compatibility data.
- **Tuning sheet:** tyre pressure (cold), gearing (final + per gear), alignment (camber, toe, caster ~4-7 deg), anti-roll bars F/R, springs, ride height, **damping with separate bump and rebound (bump about 50-75 % of rebound)**, aero F/R, **brake balance + pressure (starting 52-55 % front, 100 % pressure)**, differential (front accel/decel, centre split 50-80 %, rear accel 50-100 % / decel 0-accel). Some sheet items need the matching part installed (race suspension for springs, race bumper/spoiler for aero, sport/race diff for diff tuning); this gating matches GT.
- **Tyre model (FM4):** Pirelli-supplied data covering width, height, compound, pressure, heat, wear, sidewall, load and angle; load transfer matters; telemetry shows three thermal bands (inner/middle/outer) per tyre, pressure that rises with heat, peak grip window roughly 180-210 F. Rule of thumb used by players: centre hotter than edges = pressure too high (drop 1 psi per 5 deg difference), edges hotter = too low. Turn 10 stated they had no wet-tyre data from Pirelli (wet is the weak area; our wet/snow multipliers are our own calibration).
- **Telemetry pages:** General (inputs, boost, torque/power/rpm), Friction (per-tyre dynamic friction graphs, peak friction %), Suspension (per-corner travel), Tyres/Misc (speed, camber, temp, pressure, wear), Heat (inner/middle/outer). nig-drives already has Telemetry+ (F2, four tyres: load bar, slip ratio, slip angle...). Stage M extends it.
- **Feel ideas worth copying:** load-sensitive grip (already `loadSensitivity`), per-compound slide behaviour, turn-in vs stability trade-offs from toe/ARB/dampers, rebound shifting grip between axles during transitions, aero that costs top speed. Not copying: tyre carcass flex and per-band contact patch (too costly for the gain).

## 3. Stage A: Foundations (do first; everything depends on it)

1. **`CarBuild` + build compiler.** A pure function `compileBuild(base: PhysicsSpec, build: CarBuild): PhysicsSpec` that never mutates `base`, returns a fresh effective spec (tyres, parts, setup, ballast, conversions) and is called on garage/tune changes, never per frame. `Vehicle` takes the compiled spec instead of calling `physicsSpecFor(spec)` directly (`Vehicle.ts` L389). All `p.tire.mu` reads automatically see the effective tyre.
2. **Data-driven cars.** Replace the closed `VehicleId` union with `string` ids resolved through a catalogue (`CarSpecSheet` JSON -> `PhysicsSpec` + `VehicleSpec`). The original 7 vehicles become catalogue entries whose physics specs are the existing hand-written ones (golf19tdi, model3LrAwd) or their derived results frozen into JSON, **so the stock behaviour of today's cars is byte-for-byte unchanged** (regression gate).
3. **Settings + save layer** `src/game/save/` with versioned storage (`storage.ts`: read/validate/migrate/write with try/catch, quota handling, backup key), used by settings, garage and later career. Existing keys `nigdrives.assists` and `nigdrives.quality` are migrated into `nigdrives.settings.v1` on first run (old keys left in place one release).
4. **Input action map.** Replace the hard-coded `e.code` checks in `input/Input.ts` with `ACTIONS` (steer left/right, throttle, brake, handbrake, clutch, shift up/down, auto-selector, H-pattern gears, camera, weather, time, clock pause, assists toggle, Telemetry+, pause/menu, etc.) looked up through a bindings table (defaults = today's keys). Behaviour with default bindings must be identical.
5. **Perf + physics baselines** captured before any change: `sim-bench` results for all 7 cars (0-100, top speed, 60-0, skidpad g), and a frame-time capture script (see section 11) for RX 580 / nigian and the ThinkPad.
6. **Pause / back-to-menu path.** `Game` needs a clean "return to menu" (dispose the world, keep the app alive) because the main menu, garage and tutorial all need it. Today `Game.start()` is one-way.

**Validation gate A:** (a) `sim-bench` for all 7 stock cars is identical to the baseline within 0.1 %; (b) default key bindings reproduce every current key/gamepad behaviour (scripted check against a table of 40 inputs); (c) old localStorage keys migrate; (d) `npm run build` (tsc + vite) clean.

## 4. Stage B: Tyre compounds ("every car gets a tyre selector")

### 4.1 Model: how compounds plug into the existing slip model
Baseline compound **"All-season" = the existing numbers for each car** (so default behaviour doesn't change). Every other compound is a *delta set* applied by `compileBuild`:

```ts
interface Compound {
  id: CompoundId; label: string; family: 'road'|'sport'|'race'|'winter'|'rally';
  mu: number;          // x tyre.mu (peak friction, dry asphalt, nominal load)
  peakSlip: number;    // x tire.peakSlip
  peakAngle: number;   // x tire.peakAngle (and peakAngleRear)
  C: number;           // additive to tire.C (peak sharpness)
  slideFloor: number;  // NEW per-tyre replacement for the global SLIDE_FLOOR 0.8
  loadSens: number;    // additive to loadSensitivity
  rollRes: number;     // x rollingRes
  relax: number;       // x relaxLength
  widthM: number;      // x widthM (slicks run wider)
  inertia: number;     // x tire.inertia
  wet: number;         // x grip multiplier when weather = rain (on top of surface wetRetain)
  snow: number;        // x grip multiplier when weather = snow
  loose: number;       // x grip on gravel/dirt/grass/sand/compacted
  coldPenalty?: number;// optional: grip lost at start, recovered over warmUpS (stage M)
  priceRel: number;    // relative price, for the future economy
  lifeRel?: number;    // relative wear rate (stage M)
}
```
Two small code changes in the existing tyre path: `TireSpec.slideFloor?` (read in `Tire.ts` instead of the constant) and an **environment multiplier** `tyreEnvMul(compound, weather, surfaceKind)` applied to the `surfaceGrip` that `Vehicle.step` already computes (`SurfaceInfo` gains `kind`). The sim, ABS/TCS thresholds and regen caps then all see the same effective grip.

| Winter | 0.93 | 1.05 | 1.05 | -0.02 | 0.84 | 1.00 | 1.55 | 1.05 | 1.05 | snow 0.38 x 1.55 -> 0.59 |
| Rally (gravel) | 0.95 | 1.10 | 1.10 | -0.05 | 0.88 | 0.95 | 1.20 | 1.35 | 1.20 | gravel 0.65 x 1.35 |

Rules: real peak mu for road tyres ~0.9-1.1, slicks ~1.5-1.7 without aero, so the table spans realistic ranges; do **not** let any compound exceed ~1.6 absolute mu. Buses get only Eco / All-season / Winter. EV gets the same list (rolling resistance matters for range later). Mixed front/rear compounds allowed in the garage.
Why compounds aren't "strictly better": without wear (1.5.0), Soft slicks would always win. The trade-offs we do have in 1.5.0 are wet (0.50), snow (0.15), loose surfaces (0.68), higher rolling resistance, and a sharper peak/pop-off (C and peakSlip). Real wear and warm-up come in stage M; until then the PI class and the "Race rules" (section 5.4) are the other limiter.

### 4.3 UI

**Validation gate B:** (a) with All-season selected, every car is identical to baseline; (b) per-compound `sim-bench` skidpad lateral g and 100-0 braking monotonic with `mu`, with measured numbers inside the table's ratios +/- 5 %; (c) rain and snow runs: slick wet lateral g less than All-season wet, Winter snow braking shorter than All-season snow, Rally on gravel better than Sport; (d) ABS/TCS/ESC still engage correctly on a slick (thresholds read the effective spec); (e) real-world sanity: compare lateral g with published skidpad ranges for each tyre family (cite sources in the PR).

## 5. Stage C: Tuning and upgrades (GT-style stages + Forza-style conversions + setup sheet + PI)

### 5.1 Parts tree (each part has stages; each stage = a delta on `PhysicsSpec` fields)

| Slot | Stages | Effect on physics fields (targets) |

| Intake + exhaust | Stock, Sports, Semi-racing, Racing | torque x1.04 / x1.085 / x1.125; Racing moves peak up ~5 % rpm and costs ~3 % below 40 % redline |

| Turbo kit (turbo cars, or NA via aspiration conversion; excludes NA tune) | S1-S4 | torque x1.10 / x1.20 / x1.35 / x1.60; `TurboSpec`: `lagS` +0 / +0.05 / +0.15 / +0.30 s, `fullBoostRpm` +0 / +200 / +500 / +900, `maxBoostBar` display; S4 capped at ~+60 % (GT forum claims +125 %, not credible and not drivable here) |

**Net-new physics (honest list):** LSD (diff exists as a type but nothing reads it), downforce, centre-diff split for ICE AWD, per-tyre `slideFloor`, per-gear clutch slip already exists (clutch capacity). Each needs its own `sim-bench` test.

### 5.2 Conversions (Forza-style) and "Stage" bundles (GT-style)
- **Aspiration conversion:** NA -> Turbo / Supercharger (adds a `TurboSpec` or a no-lag blower share), or Turbo -> bigger turbo. Excludes NA tune. Price/PI penalty. Per-car compatibility list.
- **Engine swap:** pick from a small **engine library** (`engines.json`, ~25 real engine families as facts: I4 NA 1.6, I4 turbo 2.0, V6 3.0, V8 5.0, rotary, flat-6, diesel I4, inline-6 turbo...). Swap changes torque curve, redline, mass delta, `frontWeight` delta, sound character. Needs clutch/transmission/suspension upgrades to be usable (the sim punishes it naturally: clutch slip, wheelspin).
- **Drivetrain swap:** FF/FR/MR/RR/AWD per car where it is plausible (list from the catalogue entry); changes `drive`, mass, `frontWeight`, and the diff/centre-diff slots.
- **Stage presets (one-click bundles, editable afterwards):** Stage 1 "Street" = chip + sports intake/exhaust + sports tyres + brakes S + weight S1; Stage 2 "Sport" = NA S2 or turbo S2 + sports suspension + close box + 1.5-way LSD + twin clutch + weight S2; Stage 3 "Track" = NA S3 or turbo S3 + semi-slicks + custom suspension + racing intercooler/flywheel + triple clutch + weight S3; Stage 4 "Race" = race modification. Tuner-badge cars in GT2 (Mine's, Nismo, Spoon, Mugen) are **not separate cars**: they become named stage presets on the base car, which collapses roughly 40 GT2 entries into presets.

### 5.4 PI rating (D/C/B/A/S/R-style), computed by our own sim
- Bands (inspired by Forza 4 and cited in section 13): F 100-200, E 201-275, D 276-350, C 351-425, B 426-500, A 501-600, S 601-700, R3/R2/R1 701-998. **PI changes with parts and conversions and tyres, not with setup-sheet values** (Forza rule; keeps tuning from being a rating exploit).
- Method: run a short **headless bench of the actual compiled spec** in a Web Worker (the 120 Hz sim is cheap): 0-100 km/h, 0-200 km/h or time to top-speed plateau, top speed, 100-0 and 60-0 braking distance, steady-state skidpad g at 60 and 120 km/h (downforce shows up). Score each 3.0-10.0 (log scale between anchors), weight, and map to 100-998. Because the rating comes from the same physics, it cannot disagree with the game.
- Calibration anchors (check, adjust): Golf 1.9 TDI around E/D, Golf VR6 around D/C, Tesla Model 3 LR AWD around B/A, 90s hot hatch around D, R34 GT-R stock around A, Group-C style race cars R-class.
- Show PI badge + class colour in the picker, garage and setup sheet; "Race rules" filter (only cars within a PI/class band) is the hook for stage L.

### 5.5 Economy decision (needs Nigel)
- **Recommended for 1.5.0: no economy.** All parts, tyres and cars are unlocked in the sandbox garage. Parts/cars still carry `priceRel` data (GT4 price ratios are a good model: chip 1.5k, NA S1 4.9k, S2 12.5k, S3 75k, turbo S1 4.8k to S4 80k, flywheel 0.43-1k, triple clutch 4.6k, weight S1/S2/S3 1.2k/5.5k/22k, racing tyres 8.4k-47.5k, in GT4 credits) so credits can be switched on in career (stage L) without reworking the data.
- Optional later "Credits mode" toggle in the garage that uses the same prices, funded by the career.

**Validation gate C:** (a) stock builds unchanged; (b) every part stage has a `sim-bench` assertion on its target metric (e.g. Racing intake: peak power +10-15 % +/- 3 pts; weight S3: -15 % mass, 0-100 faster, braking shorter on same tyres); (c) clutch slip appears when a stock clutch meets a +60 % turbo kit (negative test); (d) LSD tests: on a 2-wheel-low-grip split-mu test, locking diff accelerates faster than open; high decel lock increases entry understeer; (e) PI monotonic for every upgrade (never goes down when adding power parts) and invariant to setup-sheet changes; (f) setup values clamp to ranges and migrate safely; (g) physics-plausibility cross-check: for 5 known cars with published acceleration/braking/skidpad numbers, the stock sim lands within +/-10 % (cite the numbers).

### 6.2 Storage and schema (localStorage, one document)
Key: `nigdrives.garage.v1` (separate keys for settings `nigdrives.settings.v1` and, later, career `nigdrives.career.v1`).

```ts
interface GarageDoc {
  schema: 1;                 // integer; bump on breaking change, add migration fn
  app: 'nig-drives';
  gameVersion: string;       // writer's version, informational
  updatedAt: string;         // ISO
  activeId: string | null;
  cars: GarageCar[];         // max 1000 (GT4's limit); soft warn at 200
}
interface GarageCar {
  id: string;                // uuid, local
  modelId: string;           // catalogue id, e.g. 'golf_19tdi', 'jp_nsx_1997'
  modelRev: number;          // revision of the catalogue entry this was saved against
  nickname: string;          // <= 32 chars, sanitised
  createdAt: string; updatedAt: string;
  paint: { body: string; accent?: string; finish: 'gloss'|'metallic'|'matte'|'pearl' };  // #rrggbb
  tyres: { front: CompoundId; rear: CompoundId; pressureCold?: { f: number; r: number } };
  parts: Record<PartSlot, { stage: number; variant?: string }>;       // absent = stock
  conversions?: { aspiration?: string; engine?: string; drivetrain?: string };
  setup: SetupSheet;         // only fields unlocked by the installed parts are honoured on load
  assists: { abs: boolean; tcs: boolean; stability: boolean };
  transmission: 'auto' | 'stick_seq' | 'stick_h';
  odometerKm?: number;
  notes?: string;
  origin?: 'sandbox' | 'career';   // reserved for stage L
}
```
- **Versioning:** `schema` integer + ordered `migrations[n]`. Load = parse -> migrate up -> validate/clamp (unknown parts dropped to stock, out-of-range setup values clamped, unknown `modelId` kept but greyed with a "model not available" badge, never deleted) -> use. A document with a newer `schema` than the app is **not** overwritten: it is loaded read-only and a backup copy `nigdrives.garage.bak` is stored. `modelRev` mismatch keeps the tune and re-clamps the setup to the new limits.
- **Writes:** debounced, atomic (serialise first, then `setItem`), quota errors caught and surfaced ("Garage not saved: storage full, export now"). Typical car about 1.2 KB, so 1000 cars is about 1.2 MB, well under the ~5 MB quota.
- **Import/export:** Export garage -> `nig-drives-garage-YYYYMMDD.json` (download), Export one car -> `.nigcar.json` and a copy-able share code (base64url of the car JSON). Import validates against the schema, shows a preview (count, models, any unavailable), offers **Merge** (new ids on collision) or **Replace** (with an automatic backup first). No remote upload anywhere.
- Electron: same localStorage; add a "show data folder"/backup button later.

**Validation gate D:** round-trip tests (export -> import -> deep-equal), corrupt/old/newer-schema fixtures, quota-full simulation, 1000-car load time under 50 ms, no data loss across a version bump, and the seeded 7 cars behave like stage-A baselines.

## 8. Stage F: Car catalogue, data pipeline, bodies

### 8.1 Pipeline: one hand-checked spec sheet in, one generated JSON out
```
data/cars/src/<make>_<model>_<years>.json   (SpecSheet: real published numbers + sources + confidence)
        |  scripts/build-cars.ts  (validate -> derive -> bench -> emit)
        v
src/game/data/cars/<id>.json                (PhysicsSpec + VehicleSpec + body params + catalogue meta; lazy-loaded)
src/game/data/cars/index.json               (small: id, make, model, years, class, body style, drive, kW, kg, PI)
```
**SpecSheet fields** (each with `source` url and `tier`: `A` = manufacturer/press kit/homologation document, `B` = reputable secondary citing A (encyclopedia with OEM cite, period road-test), `C` = estimate flagged `est`): mass (kerb), weight distribution, engine layout, cylinders, displacement, aspiration, rated power kW @ rpm, torque Nm @ rpm, redline, transmission type + ratios + final drive, drive layout, L/W/H, wheelbase, front/rear track, tyre size, Cd and frontal area (or published CdA), published 0-100, top speed, 400 m time if any, braking 100-0 if any.
**Build step rules:** a car can't be built unless tier A/B exists for mass, power (kW and rpm), torque, drive layout, L/W/H, wheelbase and tyre size; ratios are optional (synthesised and flagged `est`). Estimated values show as an "est." badge in the car card.

**Derivation** (extends `deriveSpec.ts`, same house style):
- Torque curve: archetype shapes (NA high-rev, NA low-rev, turbo petrol, diesel, V8 pushrod, rotary, kei turbo, EV) solved to hit the published **peak torque at its rpm and peak power at its rpm** (3-parameter fit; reject if power error > 2 %).
- Gearing: published ratios; else geometric spacing from gear count, 1st sized for a standing-start target, top gear from published top speed (or the existing drag-limited solve).
- Weight distribution: published; else by layout (FF 0.62, FR 0.52, MR 0.43, RR 0.38, 4WD by base layout).
- CG height and inertias: by body-style archetype (hatch 0.50 m, sedan 0.52, coupe 0.47, sports 0.43, supercar 0.38, wagon 0.55, SUV/pickup 0.65-0.70, kei 0.50), yaw inertia from mass and L/W as `deriveSpec` does today.
- Brakes: from mass and class; steering lock and ratio by class; assists default on.
- Default tyre by car class (economy -> All-season, sport/coupe -> Sport, supercar -> Sport Soft) at the **published tyre size** (radius and width from the size code).
**QA gate in the build:** headless `sim-bench` of every generated car must land within **+/-8 % of published 0-100 and top speed (+/-12 % if the car has tier-C values)**; failures fail the build and print a diff. This is the accuracy enforcement for car specs.

### 8.2 Which data is reliably available (honest)
| Data | Availability |
|---|---|
| Kerb mass, rated power/torque and their rpm, displacement, drive layout, L/W/H, wheelbase, tyre size | high for 1990s+ mass-market cars (brochures, press kits, encyclopedia entries with OEM citations); medium for low-volume/JDM kei and 1960s-70s cars |
| Track widths, gear ratios, final drive | medium-high for popular cars; patchy otherwise |
| Weight distribution | medium; tests and some press data |
| Cd / frontal area | medium (Cd common, area often missing; estimate area = 0.85 x W x H) |
| Redline | medium |
| Torque curve shape | **not published**; only 2 anchor points per car; shape comes from the archetype (flag in UI) |
| CG height, inertias, suspension stiffness, brake torque | not published; archetypes |
| Wikidata (CC0) | has fields for mass, power output, length/width/height, wheelbase for some cars; coverage is uneven, so use for cross-checks, not as the primary source (verify coverage before relying on it) |
Copying prose or tables from Wikipedia, car-data sites or brochures is not allowed; only the numeric facts, with the source URL recorded.

### 8.3 Effort per car (honest)
- With the pipeline, one researched + reviewed car is about **30-45 minutes** (find sources and tier them 15-25 min, fit/bench/fix 10-15 min, body profile or archetype choice 5-10 min). Hero cars with their own side profile add 30-60 min.
- 40 cars is about 3-4 focused days; ~240 families (the GT2 distinct families) is about 5-7 weeks of steady agent work; the full 621-entry list is not worth doing as separate cars (collapse into families + trim variants + stage presets, see 5.2).
- GT2 entries that are **fictional or prototype** (Dodge Concept Car, Ford GT90, GT-One race cars, Esprit/Elise GT1 road cars, "Drag" cars, many LM Editions) have no reliable real specs: skip or mark clearly as "approximate".
- Phases: **F1 (in 1.5.0): ~40 cars** across eras and classes (examples to pick from, subject to Nigel's taste): 1960s Shelby Cobra 427, 1966 Ford GT40, 1971 Datsun 240Z; 80s Toyota AE86 Trueno, Honda CR-X, Nissan Skyline R31; 90s Mazda MX-5 (NA), Honda Civic Type R EK9, Honda Integra Type R, Honda NSX, Mazda RX-7 FD, Toyota Supra A80, Nissan Skyline GT-R R32/R33/R34, Mitsubishi Lancer Evolution VI, Subaru Impreza 22B, Toyota MR2, Nissan Silvia S15, Lotus Elise, Mini Cooper, VW Golf IV GTI 1.8T, BMW 328i, Dodge Viper GTS, Chevrolet Corvette, Ford Mustang Cobra, Nissan Pulsar GTi-R, kei cars (Suzuki Cappuccino, Honda Beat), plus the existing 7 vehicles. **F2 (1.6.x):** about 60 more per release by make/era. **F3:** remaining families by demand.

### 8.4 Visual approach (needs Nigel)
GT's 3D models and assets are Polyphony/Sony copyright: **not used, not traced, not "inspired by" screenshots.** Our options:

Colour: per-car paint with finish; wheels/rim styles (3-4 generic designs).
**Sound:** 6-8 sound characters (I4 NA, I4 turbo, V6, V8, flat-4/flat-6, rotary, diesel, kei, EV) mapped by engine layout in `EngineSound`.

## 9. World-fidelity track (stages G, H, I, J): accurate roads, terrain, sight lines, imagery

Principle: **measure first, then change.** Each stage starts with a baseline measurement (error vs reference, frame time) and ends with the same measurement showing improvement. Nothing here adds street labels or residential names. Cities today: San Francisco, Chicago, NYC, Toronto, Kitchener-Waterloo. HRDEM is Canada-only, so Toronto and K-W get the best terrain; the US cities need a different high-res source (see H).

### 9.1 Stage G: road boundaries and off-road surfaces (ships 1.5.1)
Today: width = `WIDTH_BY_HIGHWAY[highway]` only; curbs are thin strips; bridges get sides; no barriers, no sidewalks, no shoulders; grip only via `SurfaceKind`.
1. **True widths from OSM tags.** Confirm the Overpass query returns tags (`OverpassClient.ts`; only `highway`, `surface`, bridge/tunnel are read today). Width resolution order: `width=*` (parse m/ft, ignore bad values) -> `lanes=*` x lane width (3.0 m residential/service, 3.3 arterial, 3.65 motorway) + marked parking/cycle lanes (`parking:lane:*`, `cycleway=*`) -> current class table. `oneway=yes` halves the carriageway; `lanes:forward/backward` handled; `divider`/dual carriageways are separate ways already. Clamp 2.5-30 m, log outliers.
2. **Edge treatment:** kerb height 0.12-0.15 m where `kerb=*` or urban; flush edge on rural roads with a shoulder (`shoulder=*`, default 1.0-2.5 m on primary+); sidewalks from `sidewalk=*` and footway ways (raised 0.12 m, 1.5-2.0 m default) drawn as geometry, non-drivable for AI later.
3. **Barriers and walls:** `barrier=guard_rail|wall|fence|jersey_barrier|bollard` ways and bridge parapets become **collision lines**. I did not find a collision system in the files read (`VehicleSim`, `Vehicle.step`); audit how building/water/bridge collisions work first (water handling exists in `Game.ts`/`visuals/Splash.ts`; not audited) and add a simple swept-circle-vs-segment contact response with restitution and damage-free scrape friction (no deformation).
4. **Off-road grip tied to compounds:** pass `SurfaceInfo.kind` through (stage B) so Rally/Winter/Slick multipliers apply on gravel/dirt/grass/sand; add `smoothness=*`/`surface=*` refinement (e.g. `unpaved`, `fine_gravel`) and rumble-strip noise; road-edge transition: grip blends over 0.5 m from asphalt to shoulder/grass so you can feel the edge, with tyre-compound-specific off-road drag (slicks bog in grass).
5. **Junction cleanup and lane markings:** centre/edge lines only where lanes/width support them.
**Perf budget:** +<=10 % road/curb vertices; sidewalks and barriers instanced or merged per tile; +0 draw calls per tile (merge by material).
**Validation gate G (accuracy):** (a) sample 40 road segments per city where OSM has `width` or `lanes`; rendered width vs tag within +/-0.2 m; (b) for 20 intersections per city compare road edges against ion/Bing aerial imagery in a **top-down overlay** (`scripts/overlay-check`, offline render, no labels) and log offsets > 3 m as OSM-data issues, not ours; (c) collision test: drive into a guard rail/wall at 30/60/100 km/h, no tunnelling; (d) grip table per surface x compound reproduces the targets of stage B; (e) frame time within +0.3 ms of baseline.

### 9.2 Stage H: terrain accuracy (ships 1.5.1)
**Today:** Terrarium z14 (near), z12 (mid), z11 (far); rings 6 m / 30 m / 125 m; near ring carved around roads (cut/fill, `CARVE_*`); `RoadProfile` smooths and grade-caps. Honest limit: Terrarium at z14 is an upsample of source data that in Canada is likely 20-30 m class; it cannot show kerbs, embankments or small crests accurately.

**Candidate sources (weigh):**
| Source | Resolution / coverage | Access | Licence | Verdict |
|---|---|---|---|---|
| **Canada HRDEM mosaic 1 m / 2 m** (NRCan CanElevation) | 1-2 m DTM and DSM from airborne LiDAR; 2 m mosaic has DSM everywhere in Canada and DTM only where LiDAR exists; CGVD2013 vertical datum, EPSG:3979 | STAC API `datacube.services.geo.ca/stac/api` -> Cloud-Optimized GeoTIFF range reads | Open Government Licence - Canada | **Primary for Toronto and K-W**, *if* the city bbox has LiDAR DTM (I did not run the STAC query; do that first) |
| Ontario DTM (lidar-derived) | 1 km tiles, resolution varies by project | Ontario GeoHub packages | Open Government Licence - Ontario | cross-check / alternative to HRDEM for gaps |
| **Cesium World Terrain** (ion asset 1, quantized-mesh 1.0) | global; **Canada about 30 m**, other regions vary (verify the current table on the Cesium page) | ion endpoint + token | Cesium ion ToS; attribution; community tier non-commercial; 15 GB/month streaming | **Not an upgrade in Canada** (30 m is about what we have). Good fallback for the US (SF/Chicago/NYC may reach 1 m LiDAR-class there) and for any place with no HRDEM. Verify US city coverage by sampling |
| USGS 3DEP 1 m (US) | 1 m where LiDAR | public | public domain | **candidate for SF/Chicago/NYC**; not researched in this pass, verify access path before committing |
| Copernicus GLO-30 | 30 m **DSM** (includes buildings/trees) | AWS Open Data COG | free, open | last-resort global fallback; DSM bias on roads/buildings (do not use under roads) |
| Terrarium (current) | z14 upsampled | S3 | open | keep as the **no-key, no-network** fallback |

**Recommended design:** a **DEM provider stack** behind `ElevationSampler`: `HrdemProvider` (pre-baked), `CwtProvider` (token), `TerrariumProvider` (current). Lookup order per tile: HRDEM-DTM -> 3DEP/CWT -> Terrarium; the active source and its resolution are shown in the debug HUD.
- **Pre-bake, don't stream COGs in the browser.** HRDEM is EPSG:3979 CGVD2013; reprojecting COG windows in-browser is heavy. A script (`scripts/bake-dem.py`, GDAL/rasterio, run offline on nigian) fetches each city's bbox via STAC and writes **Terrarium-compatible PNG tiles at z15-z16** (about 3.5-1.7 m/px at 43 N, 16-bit-in-RGB like the existing format) into a **map pack** (`userData/maps/<city>/` for Electron, `public/maps/` for dev), so the existing `ElevationSampler` decoder works unchanged. Size estimate: a 10 km x 10 km area at z16 is about 500 tiles, about 50 MB per city; keep packs out of git (download/bake step; documented).
- **Vertical datum consistency:** HRDEM is CGVD2013 (orthometric); Cesium terrain heights are, as far as I know, relative to the WGS84 ellipsoid (verify) which differs from orthometric by tens of metres in Ontario; Terrarium is orthometric-like. The game only needs *relative* heights, but mixed-source tiles must be offset-matched per tile edge so seams don't step. Implement per-tile bias estimation on overlap and log the residual.
- **Road-to-terrain conforming (no floating/burying):** keep the existing profile pass but (1) feed it the DTM (not DSM; bridges/tunnels stay level-interpolated as today), (2) grade the road bed first and **cut/fill the terrain to the road surface** with side-slopes from a slope rule (cut 1:2, fill 1:3 where heights differ > 0.5 m) instead of the fixed `CARVE_SHOULDER = 7`, (3) shoulder/kerb heights follow the road's cross-fall, (4) verify with a per-vertex test that every road vertex is within 5 cm of the rendered terrain on non-bridge spans.
- **Embankments and cuts:** derived automatically by the slope rule above; visible as real slopes; with a "highway grade" cap (motorway <= 6 %, others <= 12-15 %) to detect bad DEM.
- **Near-ring resolution:** with 2 m data the near ring should be 2-3 m cells within 400 m of the player and ~6 m beyond (clipmap-style) rather than uniform 6 m; this needs a new ring layout: **budget +300-600 k triangles at most on High**, built in a worker.
**Perf budget:** DEM decode and ring build off the main thread (Web Worker + `createImageBitmap`), main-thread slice <= 2 ms; ring rebuild never causes a frame over 25 ms; memory +<= 150 MB.
**Validation gate H (accuracy):**
1. **Spot-height benchmark:** 200 points per city: OSM `ele=*` nodes (peaks, benchmarks, some bridges/transit stations if tagged), plus any survey control points available from NRCan/Ontario (verify availability), compared to each source. Report RMSE and max error per source; expected HRDEM <= 0.5 m, Terrarium several metres (this documents the improvement and catches datum bugs).
2. **Cross-source check:** sample 1000 random points: HRDEM vs CWT vs Terrarium; flag |delta| > 5 m clusters (usually DSM contamination, datum or reprojection errors).
3. **Road fit:** 0 road vertices more than 5 cm off the rendered surface (non-bridge); max longitudinal grade on motorways < 8 % (report offenders as data issues).
4. **Visual check:** known features: Niagara Escarpment/Hamilton-Burlington cut, Don Valley and Humber valleys (Toronto), the Grand River valley (K-W), Lake Ontario shore stays consistent with the bundled shore data (`shore-west-ontario.json`).
5. Frame time within budget on RX 580 (nigian) and ThinkPad.

### 9.3 Stage I: sight lines, LOD and streaming (ships 1.5.2)
Today: fog 350-7000 m clear, far plane 12 km; rings out to +/-8 km; 5x5 tile window of roads/buildings (`LOAD_RADIUS = 2`); buildings and roads load per tile; shadow map 1024-2048 over a 380 m shadow camera.
1. **Draw distance setting** (Options): Near / Normal / Far / Ultra controls tile load radius, building draw distance, fog range and ring sizes together; default chosen per measured frame time.
2. **LOD:** (a) buildings beyond ~600 m switch to merged block silhouettes or are dropped to a cheap instanced box set (flat-shaded, no normal map) up to ~2.5 km so distant streets and skyline stay visible; (b) road ribbons beyond ~500 m switch to a 2-vertex-per-sample low-detail ribbon without curbs/markings; (c) far terrain ring keeps z11/z12; (d) impostor/billboard for skyline towers (NYC/Chicago/Toronto) is a stretch goal.
3. **Streaming:** keep loading ahead along the velocity vector (bias the tile window forward by speed), prioritise by view cone, cancel stale requests when speed changes, and keep a persistent IndexedDB cache of Overpass tiles (OverpassCache exists) so revisits are instant; all parsing already async, move building/road geometry generation to a worker if profiling shows main-thread spikes.
4. **Occlusion over hill crests:** the terrain is a heightfield, so crest occlusion is largely free via the depth buffer; the real problem is *pop-in on the far side*. Fix with prefetch ahead of crests, fog/atmospheric haze scaling, and **cheap software occlusion culling**: a coarse horizon test against the terrain ring (skip building batches wholly below the line of sight from the camera) to save draw calls, not to change what you see.
5. **Driver-eye cockpit camera:** a modelled interior for the generated bodies (dash silhouette, A/B pillars, mirrors, steering wheel with arms turning) plus **eye-point per car** (seat height from body archetype), correct FOV (60-100 deg slider), head-bob off by default, look-around with mouse/right stick, and shadowless interior. Bonnet-cam, bumper-cam, chase-cam variants. Sight-line realism: pillar blind spots, windshield reflection off by default.
6. **Atmosphere and fog tied to weather** already exist; add aerial perspective tint (Rayleigh-ish) so distant terrain fades to horizon colour correctly instead of flat fog.
**Perf budgets (proposed, measure first):** High preset >= 60 fps on the RX 580 (nigian) at 1080p; Medium >= 60 fps on the ThinkPad **without** the miner and >= 40 fps **with** it (today it measures about 44 fps with the miner running, so protect that number: no regression below 44); <= 1,500 draw calls and <= 3.5 M triangles on High; main-thread long tasks (> 50 ms) = 0 during steady driving; streaming tasks <= 2 ms/frame average. Every LOD change is benchmarked on both machines with the same scripted route (no servers started by the agent; record frame times with the in-game FPS counter and the `__nig` debug hook, run on the user's side).
**Validation gate I:** scripted 5-minute loops in each city (fixed route, weather clear, time 12:00) with p50/p95/p99 frame times before/after; pop-in count (number of building batches that appear within 400 m of the camera) before/after; screenshots from fixed camera poses at 5 distances; cockpit view FOV and eye-height audit per car.

## 10. Later stages: M (tyre thermal model), K (catalogue growth), L (career)

### 10.1 Stage M: advanced tyre model (1.5.3)
- Per-wheel state: core temperature (heats with slip power `|Fx*vslipx| + |Fy*vslipy|`, cools with airflow and ambient), **cold pressure setting** -> hot pressure by gas law, wear scalar.
- Effects: grip vs temperature is a bell around the compound's window (FM4: roughly 180-210 F for race tyres; road tyres wider and lower), pressure shifts contact patch (too high -> peaky, early loss; too low -> sluggish, hot edges), wear reduces mu up to -15-20 % and raises `peakSlip`; `coldPenalty` from the compound table; rain and track temperature scale heating.
- Camber/pressure telemetry bands (inner/middle/outer) are **derived**, not simulated per band (camber and load distribution -> three numbers), which is enough to reproduce Forza's tuning feedback loop (centre hotter -> too much pressure, 1 psi per 5 deg) without a contact-patch model.
- **Telemetry+ pages** (extend `ui/TelemetryPlus.ts`): General (inputs, boost, torque/power/rpm), Friction (per-tyre peak %), Suspension (per-corner travel), Tyres (temperature, pressure, wear, camber), Heat bands. Optional setting "Tyre wear: off / normal / fast" and "Pit reset".
- **Validation gate M:** warm-up curve, wear curve and pressure sensitivity checked against published tyre behaviour (cite sources); compounds ordered correctly over a 10-lap simulated run; telemetry rules reproduce (set pressure +5 psi -> centre hotter).

### 10.2 Stage K: catalogue expansion (1.6.x)
Batches of ~40-60 cars per release, ordered by Nigel's picks, each batch passing the F pipeline and bench gate. The CSV order of effort: JDM hero families (Skyline, Supra, RX-7, NSX, Impreza, Evo, MX-5, Civic/Integra, Silvia/180SX, MR2, Celica), then European (Golf/Beetle, Lotus, Mini, Peugeot/Renault/Alfa/Fiat/Lancia), then US muscle and supercars, then kei cars, then race/special editions as presets. Target of ~240 families. Not promised for 1.5.0.

### 10.3 Stage L: Career mode (1.7, alongside the sandbox; about 20-35 days)
**Structure:** Career lives beside the sandbox. Separate save (`nigdrives.career.v1`), separate garage inside it, credits, owned parts and licences. Sandbox garage stays fully unlocked. "Career" tile on the main menu; switching never touches the other save.
- **Progression:** licences (L/B/A/S-style tests: brake, corner, slalom, launch, drift gate; bronze/silver/gold times) unlock event tiers by **PI class** (E -> S) and **race rules** (FF only, RWD only, era, max PI, tyre limit, power limit), like GT's "Sunday Cup" ladders; unlocks: events, dealer stock (used lot rotates GT3-style), parts stages, tyre families, conversions.
- **Economy basics:** starter 10k credits and a garage with one cheap car (GT2 style) or a gifted starter car; car price = f(PI, age, rarity) (`priceRel` x base curve); part price from the table in 5.5; prize = class base x position share (1st 100 %, 2nd 60 %, 3rd 40 %, others 20 %) x difficulty; first-time medal bonus; sell-back 50 % (60 % when same make). Target pacing: a first 90s compact in the 8-15k range, E-class events paying 1-3k, a D-class upgrade path reachable in ~10 events, S-class cars an hour+ of play. Keep all numbers in `data/career/economy.ts` and tune with a spreadsheet script, not by hand.
- **Race types feasible on the OSM map (nothing exists today; no AI, no checkpoints, no laps):**
  1. **Time trials / point-to-point:** two points on the road graph, checkpoint gates every N metres, wrong-way/shortcut checks, medal times set by a reference run of the stage-C bot (below). Cheapest, lowest risk; ship first.
  2. **Circuits from street loops:** a loop found in the **road graph** built from loaded ways (shared node ids; not available today, `RoadIndex` only does nearest-segment queries): pick a closed loop 2-6 km with enough curvature and length, set gates and a lap counter. Needs a pre-selected, stored route per city (polyline + node checksum) so events don't change when OSM edits.
  3. **Ghosts:** record pose (x, z, yaw, speed) at 30 Hz per run (about 1 KB per 3 s, small) and replay; personal-best ghost and "reference" ghost. Recording poses, not inputs, avoids determinism problems.
  4. **Drag/launch and top-speed runs on long straights:** easy once timing gates exist.
  5. **AI opponents:** the big item (below); phase L3.
- **Events never use street names:** events are "Toronto Loop 3", "K-W Point-to-Point 2" etc.; no residential names on screen.
- **Career save schema:**
```ts
interface CareerDoc {
  schema: 1; app: 'nig-drives'; gameVersion: string; updatedAt: string;
  profile: { name: string; credits: number; xp?: number };
  garage: GarageCar[];                     // same GarageCar type; origin: 'career'
  ownedParts: Record<string /*carId*/, PartId[]>;   // purchased parts (sandbox has all)
  licences: Record<string, { medal: 'none'|'bronze'|'silver'|'gold'; bestMs?: number }>;
  events: Record<string, { completed: boolean; bestPlace?: number; bestMs?: number; medal?: string; wins: number }>;
  unlocks: string[];                       // event/car/part ids
  usedLot?: { seed: number; refreshedAtStep: number };
  ghosts?: Record<string /*eventId*/, GhostRef>;
  settings?: { raceRulesEnforced: boolean };
}
```
Separate versioning/migration/backup from the garage doc, same export/import mechanism.
- **Phasing:** L1 licences + time trials + credits + dealer/parts purchase (4-6 d each for UI and rules); L2 circuits + ghosts; L3 AI opponents.
- **Risks (see also section 12):** **AI drivers are the big one.** What exists: nothing (no path following, no opponents, no traffic). Required: a road-graph router, a racing line (from curvature + lateral offset), a driver controller that drives the *real* `VehicleSim` at 120 Hz through the same inputs a player has (throttle/brake/steer with friction-circle-aware target speed from the tyre's mu and curvature), corner/overtake/collision rules, rubber-banding limits, and car-to-car collision (the physics has no inter-car contact today). Expect 12-20 days alone and lots of tuning; budget 2 iterations. Mitigation: ghosts first; "AI" = replaying recorded reference laps with small per-lap variation (fake) as a first pass; real AI as a later optional milestone. Other risks: OSM edits changing a stored route (store polyline + tolerance + checksum, fall back to snapping); road data offline (event only available if the tiles are cached); fairness of time medals across weather/time (fix weather and time per event); economy exploits (cap repeat prizes).
